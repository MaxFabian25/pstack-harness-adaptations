### Autopilot-full

**Each PR has one implementation owner and an independent verification swarm. In T3 Code the parent owns watches and merging. Outside T3 Code the owner carries the PR through merge. Nothing merges until the swarm has proven the code that lands.**

A verdict covers one patch and green CI covers one head. Step 4 runs a full swarm once, and again only for a major change. The patch-id rule in `playbooks/shipping.md` can carry a lane's result, and every new head needs its own green CI.

1. **The operator's gates come first.** The grant covers only the queue's items, so items the operator names as theirs and PRs outside the queue stop at merge-ready. A request to state the plan is not a go.
2. **Spawn one owner per PR, and keep its work where a replacement can find it.** Resolve the forge once for the program. GitHub CLI (`gh`) is the default. If `command -v origin` succeeds and Origin can resolve the repository, use `origin pr` for every PR operation. Otherwise stay on `gh` and record the fallback. Never require Graphite (`gt`). Each owner is an isolated owner agent (a remote cloud worker where the harness offers one, else an isolated writer on its own branch, per [harnesses.md](../references/harnesses.md) (Cloud and isolated work)) that builds, opens its PR per `playbooks/opening-a-pr.md`, and proves the change on the real artifact. In T3 Code the owner returns its head and evidence. The parent owns PR watches, dispatches scoped fixes, and merges once steps 4 and 5 clear the PR. Outside T3 Code the owner babysits to green per `playbooks/babysit.md` and merges once cleared.

   Open the PR early so CI and bots run alongside the work. The code is ready only after the slop-strip (the `deslop` skill from the `cursor-team-kit` plugin (`/deslop`)) and the `/no-comments` pass, so the full swarm runs on finished code. Then rebase onto current trunk and report the code-ready head before self-proof, so verification runs on the base the patch lands on. Report every later head and the self-proof evidence. In T3 Code the parent reports merge-ready after CI and babysit. Outside it the owner does. Fix rounds stay on that base unless trunk conflicts, breaks CI, or lands a known concurrent change to the same files, because each rebase restarts CI. Run the repo's checks for the touched paths on the committed head before the code-ready push and before a later push that needs a verifier.

   Assume the owner's machine dies. Soon after starting, push and start a decision trail in the root's agent store (per [harnesses.md](../references/harnesses.md) (The agent store)) per the **show-me-your-work** skill, then push each finished unit before you start the next. Whoever spawns a subagent records its id, state, and a stuck-after runtime from past runs of its kind in that store, so the root can probe it if the parent dies. Force-push only your own branch, with `--force-with-lease` pinned to the SHA you last pushed or took over, and on any push you did not make, stop and report to the root.
3. **Run owners in parallel off trunk, never stacked,** so each PR lands on its own.
4. **Swarm-verify once.** A full swarm runs once, at the code-ready head. Another full swarm runs only for new behavior, a redesign, or a large new diff. A rebase, a merge-conflict resolution, or a minor fix gets a single verifier at the new head, and a wording-only change gets none. Fan out independent verifiers at the code-ready SHA per the **swarm** skill. Give each a distinct behavioral check. Reuse returned check output for the same head, inputs, and environment, and rerun when a change, failure, or unresolved concern warrants it. Follow the repository's rule for full CI suites. Verifiers still prove the load-bearing behavior live on the real surface through its control skill (such as `control-ui` or `control-cli` from `cursor-team-kit`) or a named driver, and audit the diff. The verdict is not clean without the live lane or before you audit the merge-ready report's receipts.

   Block a PR only for a problem you can show, with a failing run at the head or a doc line the PR made wrong. A problem the PR's base already has, whether trunk or the PR below it in a stack, doesn't block unless the PR copies it or newly reaches it. Only a bug a user would hit, a failed gate, or a wrong shipped doc blocks, and everything else goes in a follow-up.
5. **Merge only what you verified, tested on the trunk it lands on.** The parent merges in T3 Code, and the owner merges outside it. Green CI alone never authorizes a merge. Once the swarm's lanes have started, merge prep rebases onto current trunk, reports the new head, and waits for green CI.

   Right before merging, fetch trunk and ask whether its changes can affect the patch, because rebasing for every trunk move never ends. Rebase and wait for CI when the code that would land was never tested, as with a conflict, a file both sides changed, or a change to which checks run for the PR. A lockfile both sides changed needs no rebase when a frozen install passes on the merge result and the packages the PR changes resolve there as on the head, because that install tests the lockfile that would land, and a failing install means the rebase must repair it. When trunk changed a caller of the patch or something the patch depends on, such as code it calls or a dependency version, run the patch's checks on the merge result and merge on a pass. Otherwise merge. If trunk would force a third rebase past merge prep, hold and report to the root, which sequences the colliding work.
6. **Run the root layer.** Anything that loosens a gate, such as a raised budget or an allowlist entry, needs a verifier's proof and then your fresh countersign, because the owner is the one who wants green. Under a grant that covers approvals, that countersign is the approval, and the owner's record of it points at your countersign for a lane to check. A disabled or soft-failed check always comes out, because it stops guarding every case. Never give or bypass an approval the forge enforces, because no countersign covers it.

   In T3 Code, use the host's completion and persistent PR-watch contracts. The parent handles each wake, checks the returned evidence, and dispatches the next scoped action. Use the current tool descriptions for waits and restart recovery.

   Outside T3 Code, on the operator's go, arm `/loop 1h` or the Codex equivalent in [harnesses.md](../references/harnesses.md) (Tools) to audit until no delegated work is left. Local background owners end with the root's session, and remote or cloud owners survive it. After a restart, re-arm the cadence if it ended and replace every local owner from its pushed branch and trail. Each tick re-reads this playbook and fixes drift, such as an unreported head or an unrecorded agent, by having its owner record it. It probes every agent, down to the leaf lanes, per the liveness row of [harnesses.md](../references/harnesses.md) (Cloud and isolated work), and judges each by its side effects. An agent is stuck when it errors, cannot start turns, or shows nothing new past its stuck-after runtime, and so is an owner that has neither pushed nor written a trail row by the first tick. One waiting on you or the operator is not stuck, so answer it. Replace a stuck agent at once, without waiting for its stop to land. A tick that changed something for the operator ends by catching them up per the **ketchup** skill, and one that changed nothing stays quiet.
7. **Stand down at once on the operator's stop.** A hold reaches every owner as a zero-writes order. Each reports where it stands and keeps its brief until the operator releases it.

**Reply:** catch the operator up per the **ketchup** skill, covering each PR's state and verdict, what merged, countersigns and why, open operator gates, and parked follow-ups, with links to each PR and the trails.
